## 1. 现状（实测，不是印象）

数据文件：`Sources/LunisolarCalendarApp/Resources/huangli_db.json`，**419 KB**。

```json
{ "v": 1,
  "range": ["2024-01-01", "2028-12-31"],
  "count": 1827,
  "days": {
    "2024-01-01": { "y": ["祭祀","祈福",...],   // 宜（字符串数组）
                    "j": ["诸事不宜","嫁娶",...],// 忌（字符串数组）
                    "c": "马",                   // 冲（**已去掉「冲」字**）
                    "s": "南",                   // 煞（**已去掉「煞」字**）
                    "w": "金箔金",                // 五行纳音
                    "g": "喜神:东北 财神:西南" }   // 神位
  } }
```

- 查询入口：`HuangliDBProvider.resolve(date:)` → `Resolved { huangliDay, source }`；
  命中返回 `source == .discreteDB`，未命中回落到 `HuangliGenerator.algorithmGenerate`
  （`Support/HuangliDBProvider.swift:102-135`）。
- key 由**设备时区的日历分量**生成（`dayKey(for:calendar:)`，`HuangliDBProvider.swift:92-99`），
  与设备时区解耦——这点已被专门修过，换源时**不要**改成别的口径。
- 范围外（2024 前 / 2028 后）自动用同一套干支规则实时推导，不会空窗。

### 数据质量（这是你要换源的原因）

| 指标 | 实测 |
|---|---|
| 天数 | 1827（2024-01-01 ~ 2028-12-31，与 `range` 自洽） |
| 不同「宜」组合 | **9 种** |
| 不同「忌」组合 | **10 种** |
| 规律 | 按当日天干分组，**每 10 天整循环** |
| 来源 | 由 `HuangliGenerator` 的 `yiPool`/`jiPool` 规则集推导（`Models/Huangli.swift:75`、`:109`），JSON 只是同一规则的离线缓存 |

### 顺手发现的一处不一致（与换源无关，但要先知道）

`days` 里每条都带一个 **`a` 字段**（1827 条全有），但：

- 当前生成工具 `Tools/gen_huangli_db/main.swift:29-36` **不写 `a`**；
- 解码类型 `HuangliDBEntry` 的 `CodingKeys`（`HuangliDBProvider.swift:8-16`）**也不读 `a`**。

也就是说：**已提交的 JSON 无法用已提交的工具复现**（它是更早版本的工具生成的，`a` 现在是死字段）。
换源时会整体重写这个文件，这件事会顺带消失；但如果你打算「先不换源，只重新生成一版」，
记得先生成、再核对 `git diff`，别以为跑一遍工具就能得到同样的文件。

## 2. 换源需要改什么

### 情况 A：新源能对齐现有 6 项字段 → **只换 JSON**

供应商（或你）产出符合下面契约的 `huangli_db.json`，其余不动：

| 契约 | 要求 |
|---|---|
| key | `yyyy-MM-dd`，**东八区历法日期**，不是瞬时 |
| `y` / `j` | 字符串数组，汉字词条（如 `祭祀`、`诸事不宜`），**不要带书名号/顿号** |
| `c` | 单个地支字，**不要带「冲」前缀**（读入时拼接，见 `HuangliDBProvider.swift:120`） |
| `s` | 单个方位字，**不要带「煞」前缀** |
| `w` | 纳音五行字符串，如 `金箔金` |
| `g` | 神位串，形如 `喜神:东北 财神:西南`（半角冒号 + 半角空格分隔） |
| root | 必须有 `v` / `range` / `count` / `days`，且 `count == days.count`、`range` 与数据自洽 |

配套必改的**文案与测试**（这两处不改会直接暴露成 bug / 失败）：

1. `HuangliDBProvider.coverageDescription`（`HuangliDBProvider.swift:135-152`）
   现在写的是「**按传统干支规则推导**」。换了权威源之后这句就不对了，必须改。
   同时 README 有「表述边界」一节，明确要求**不得**把该数据称为「权威 / 经核验」——
   若换成付费权威源，这条约束要由你决定是否解除，我不会自行改。
2. `HuangliDBProviderTests.testDBConsistentWithAlgorithmForRange`
   （`Tests/LunisolarCalendarTests/HuangliDBProviderTests.swift:82`）
   这条断言「**库内数据与算法推导一致**」。换权威源后它**必然失败**——不是 bug，是断言本身过时了。
   应该改判据为「库自身结构自洽（key 连续、字段非空、数量与 range 相符）」，
   而不是「与算法一致」。这条我会一并改。

**情况 B：字段对不齐 → 写一个转换脚本**

如果新源是 CSV / Excel / API / 字段名不同，需要一个离线转换脚本，产出上面的 compact JSON。
建议放 `Tools/convert_huangli/`（与既有 `Tools/gen_huangli_db/` 并列），好处是：
一次性跑完、可复查、不把供应商的格式带进 App 运行时。

常见的对不齐与建议处理：

| 新源情况 | 处理 |
|---|---|
| 缺「神位」「纳音」 | 这两项继续由现有算法推导（混合来源），**但 UI 必须能说明来源**，不能含糊 |
| 宜忌用词与现库不同（如「开业」vs「开市」） | 无需适配：宜忌是**纯展示**文本，没有任何逻辑或统计依赖它（已确认） |
| 只覆盖部分年份 | `range` 按实际写；范围外自动 fallback 到算法推导 → **会出现「库里权威、库外自造」的混合**，必须在文案里讲清，否则等于自欺 |
| 数据量远超 419 KB | 见 §3 体积策略 |

## 3. 体积策略（换源后大概率要面对）

现库 419 KB 全量 bundle 进 App。权威源通常一年 365 天 × 更细的词条，体积可能翻几倍。
三个选项：

1. **继续全量内置**：最省事，但安装包变大、更新要发版。
2. **按年/按范围分片内置**：只内置近几年，更早的按需。
3. **首次启动按需下载 + 本地缓存**：包最小、可更新，但要引入网络与缓存失效逻辑，
   且要处理「无网时黄历不可用」——现在是纯离线功能，这个 trade-off 会伤到体验。

我的建议：**先按 1 或 2 做**，把「在线更新」留到确有运营需求时再说；现在这个库一年才动一次，
不值得为它引入网络层。

## 4. 你要跟供应商确认的清单

- ☐ **覆盖年份范围**（黄历按年出版，通常每次只给 1–2 年）与**更新频率**、后续年份怎么续。
- ☐ **授权范围**：能否内置于 App 离线分发？能否随包分发？是否需要署名/版权页？
  是否需要按装机量付费？
- ☐ **字段清单**能否对齐 §2 的 6 项（尤其是「宜/忌」是词组列表还是分级结构）。
- ☐ **数据格式**：CSV / Excel / JSON / API？有没有稳定的机器可读格式（关系很大，
  决定要不要我写转换脚本）。
- ☐ **是否含节气与农历**——**不需要**，我们已有自己的农历与节气实现，别为重复字段付钱。
- ☐ **价格与年费**、试用/样张（**强烈建议先要 30 天样张**，我可以直接把它转成 JSON
  跑一遍现有测试，验证格式能不能对齐，再决定签不签）。
