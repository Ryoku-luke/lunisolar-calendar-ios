## D-01 系统日历重复事件导入坍缩为最后一次 occurrence

### 根因

`EKEventStore.events(matching:)` 展开重复事件后，每个 occurrence 的 `eventIdentifier` 相同；[CalendarImportProvider.swift:87](../Sources/LunisolarCalendarApp/Support/CalendarImportProvider.swift) 用该标识生成 `sourceID`，[SystemImportBridge.swift:100-101](../Sources/LunisolarCalendarApp/Support/SystemImportBridge.swift) 再由 `sourceID` 生成确定性 UUID。所有 occurrence 得到同一个 UUID，`EventStore.merge` 走同 id 更新，后写覆盖前写。

### 修复策略

不修改 UUID 种子（保持存量事件 ID 稳定），而是在**映射前按 sourceID 去重，保留窗口内最早的一次 occurrence**。这样：

- 一条重复系列只导入一条事件，且保留原 `repeatRule`；
- 原 `sourceID = "ek:<identifier>"` 不变，旧数据在下次导入时仍命中同一 UUID，不会产生副本；
- 去重逻辑放在 `SystemImportMapper`（Linux 可测），而不是 EventKit 内。

### 具体改动

**文件：** [SystemImportBridge.swift](../Sources/LunisolarCalendarApp/Support/SystemImportBridge.swift)

```swift
public nonisolated static func toCalendarEvents(_ dtos: [SystemImportEvent]) -> [CalendarEvent] {
    // 同一 sourceID 只保留最早的一条：
    // - EventKit 会把重复事件展开成多个 occurrence，但它们的 eventIdentifier 相同；
    // - 若逐条映射，同 UUID 会在 merge 中互相覆盖，最终只剩最后一次。
    var bySource: [String: SystemImportEvent] = [:]
    for dto in dtos {
        if let existing = bySource[dto.sourceID] {
            // 取窗口内最早 occurrence 作为系列锚点，保留其规则
            if dto.startDate < existing.startDate {
                bySource[dto.sourceID] = dto
            }
        } else {
            bySource[dto.sourceID] = dto
        }
    }
    // 稳定排序，保证导入结果与顺序无关
    return bySource.values
        .sorted { $0.sourceID < $1.sourceID }
        .map(toCalendarEvent)
}
```

`CalendarImportProvider.map` 保持现状，不改 `sourceID` 格式。

**可选日志：** 在 `CalendarImportProvider.fetchEvents()` 中记录“原始 N 条，系列去重后 M 条”，便于排查。

### 已知边界（写入 PR 说明）

- 若系列首次 occurrence 早于导入窗口，锚点会落在窗口内第一次出现的那天；对 daily/weekly/yearly 的时分与月日无影响，对 monthly 的 31 号在小月窗口可能锚成 30/28 号。若产品要求严格锚定原始 DTSTART，需要改为“只取主事件 + EventKit recurrenceRule 原始 start”，作为后续增强。
- EventKit 的 `interval`、`daysOfTheWeek` 仍会丢失（当前 `map` 只看 frequency）。这与 D-08 的 RRULE 语义问题同源，建议与 D-08 阶段二合并处理。

### 回归测试

## D-02 系统日历全天事件导入多显示一天

### 根因

EventKit 全天事件的 `endDate` 是**排他**的次日 00:00；[CalendarImportProvider.swift:90](../Sources/LunisolarCalendarApp/Support/CalendarImportProvider.swift) 原样传给 DTO，[SystemImportBridge.swift:102-113](../Sources/LunisolarCalendarApp/Support/SystemImportBridge.swift) 也未归一化。ICS 路径已在 [DataPortability.swift:329-341](../Sources/LunisolarCalendarApp/Support/DataPortability.swift) 做了 `-1s`，两条路径不一致。

### 修复策略

在 **Mapper** 归一化，而不是在 EventKit Provider 内：

- 只处理 `isAllDay == true` 且 `endDate` 恰为本地 00:00 的情况；
- `endDate = endDate - 1 秒`，与 ICS 路径、`CalendarEvent` 的 inclusive 语义一致；
- 非全天 / 非零点端点不做改动，避免误伤 Stub Provider 与联系人 DTO。

### 具体改动

**文件：** [SystemImportBridge.swift](../Sources/LunisolarCalendarApp/Support/SystemImportBridge.swift)

```swift
private nonisolated static func normalizedEndDate(for dto: SystemImportEvent) -> Date? {
    guard dto.isAllDay, let end = dto.endDate, end > dto.startDate else {
        return dto.endDate
    }
    let cal = Calendar(identifier: .gregorian)
    let c = cal.dateComponents([.hour, .minute, .second], from: end)
    // EventKit 全天结束是"次日 00:00"（排他）；本 App 存 inclusive 23:59:59
    if c.hour == 0, c.minute == 0, c.second == 0 {
        return end.addingTimeInterval(-1)
    }
    return end
}

public nonisolated static func toCalendarEvent(_ dto: SystemImportEvent) -> CalendarEvent {
    let uuid = deterministicUUID(from: dto.sourceID)
    var ev = CalendarEvent(
        id: uuid,
        title: dto.title,
        type: dto.eventType,
        startDate: dto.startDate,
        endDate: normalizedEndDate(for: dto),
        isAllDay: dto.isAllDay,
        // 其余字段不变
        location: dto.location,
        notes: dto.notes,
        repeatRule: dto.repeatRule,
        priority: dto.priority
    )
    // ...原有 isNotified / updatedAt 逻辑保持不变
    return ev
}
```

### 存量数据

已导入的错误全天事件无法可靠区分“本来跨两天”与“多出一天”，不做自动修复。可在导入设置页提供“重新导入系统日历”提示，用户重新导入时同 UUID 会更新为正确端点。

## D-03 重复规则边界语义不一致

### 根因

[CalendarEvent.swift:262-317](../Sources/LunisolarCalendarApp/Models/CalendarEvent.swift) 的 `occurs(on:)`：

- `.yearly` 只比较月/日 → 2/29 平年消失；
- `.monthly` 只比较 `day` → 31 号小月消失；
- `.workday` 只看 `weekday 2...6` → 法定节假日照常提醒、调休补班日不提醒。

### 修复策略

统一采用“**回退到该月/该年最后一个有效日**”和“**工作日 = 非周末且非法定节假日，或调休补班日**”的口径，与 `CountdownEvent.nextAnniversary` 的 2/29 回退保持一致。

### 具体改动

**文件：** [CalendarEvent.swift:262-284](../Sources/LunisolarCalendarApp/Models/CalendarEvent.swift)

```swift
case .workday:
    guard target >= start else { return false }
    let weekday = cal.component(.weekday, from: target)
    switch HolidayProvider.info(for: target).type {
    case .workday:
        return true                     // 调休补班日（可能是周末）
    case .holiday:
        return false                    // 法定节假日
    case .normal:
        return weekday >= 2 && weekday <= 6
    }

case .monthly:
    guard target >= start else { return false }
    let startDay = cal.component(.day, from: start)
    let targetDay = cal.component(.day, from: target)
    let daysInTargetMonth = cal.range(of: .day, in: .month, for: target)?.count ?? 30
    let expectedDay = min(startDay, daysInTargetMonth)   // 31 号 → 小月按最后一天
    return targetDay == expectedDay

case .yearly:
    guard target >= start else { return false }
    let tm = cal.dateComponents([.month, .day], from: target)
    let sm = cal.dateComponents([.month, .day], from: start)
    guard tm.month == sm.month else { return false }
    if sm.month == 2, sm.day == 29 {
        // 平年回退 2/28（与倒数日 nextAnniversary 口径一致）
        let isLeap = cal.range(of: .day, in: .year, for: target)?.count == 366
        return isLeap ? tm.day == 29 : tm.day == 28
    }
    return tm.day == sm.day
```

### 兼容性

- `.monthly` 对 1~28 号完全无影响；只改变 29/30/31 号在小月的行为。
- `.yearly` 只改变 2/29 起点事件在平年的行为。
- `.workday` 在 2027 年数据缺失时回退为“周一至周五”，与旧行为一致，不会更差。

### 回归测试

```swift

func testYearlyFeb29StillMatchesFeb29InLeapYear()
func testMonthly31FallsBackToLastDayOfShortMonth()   // 1/31 → 2/28（2026）

```

**验收：** 上述 7 个用例全绿；修改前后 1~28 号 monthly 用例行为不变。

## D-04 未来才开始的重复提醒提前触发

### 根因

[NotificationManager.swift:352-399](../Sources/LunisolarCalendarApp/Support/NotificationManager.swift) 对 `.daily/.weekly/.monthly/.yearly/.workday` 全部使用 `UNCalendarNotificationTrigger(dateMatching:repeats: true)`，匹配分量只有时分/星期/日/月，**没有起始日期**。系统从调度当刻起按规则触发。

### 修复策略

引入“重复触发计划”纯函数：

- `effectiveStart <= now`：保持现有 repeating trigger；
- `effectiveStart > now`：只排一条**首发一次性**通知（`repeats: false`），标识符加 `-first`；待首发时刻过去后，下一次 `rescheduleAllReminders`（启动/回前台/编辑保存）自然切换为 repeating 版本。
- `.workday` 的首发日需要从 `effectiveStart` 起找到第一个“工作日”（跳过周末与法定节假日）。

> 已知限制：若用户从首次提醒后长期不再打开 App，后续重复提醒不会自动安装。这是 iOS 没有“带起始日期的 repeating trigger”所决定的；App 在启动/回前台都会重排，实际影响可控。若要彻底消除，需改为“预排 N 条一次性 occurrence”，会与通知 64 条配额冲突（第一轮 P2-2），不建议在本项内做。

### 具体改动

**文件：** [NotificationManager.swift](../Sources/LunisolarCalendarApp/Support/NotificationManager.swift)

新增纯函数（便于单测）：

```swift
enum RepeatingTriggerPlan: Equatable {
    case repeating
    case deferredFirstOccurrence(Date)
}

static func repeatingPlan(effectiveStart: Date, now: Date = Date()) -> RepeatingTriggerPlan {
    effectiveStart > now ? .deferredFirstOccurrence(effectiveStart) : .repeating
}

/// workday 首发日：从 start 起找第一个真正的工作日
static func firstWorkday(onOrAfter start: Date, calendar: Calendar) -> Date {
    var day = calendar.startOfDay(for: start)
    for _ in 0..<14 {
        let weekday = calendar.component(.weekday, from: day)
        let info = HolidayProvider.info(for: day)
        let isWorkday: Bool
        switch info.type {
        case .holiday: isWorkday = false
        case .workday: isWorkday = true
        case .normal:  isWorkday = weekday >= 2 && weekday <= 6
        }
        if isWorkday {
            return calendar.date(
                bySettingHour: calendar.component(.hour, from: start),
                minute: calendar.component(.minute, from: start),
                second: 0, of: day
            ) ?? day
        }
        day = calendar.date(byAdding: .day, value: 1, to: day) ?? day
    }
    return start
}
```

在 `buildNotificationRequests` 的重复分支统一加前置判断：

```swift
let plan = Self.repeatingPlan(effectiveStart: effectiveStart)
if case .deferredFirstOccurrence(let first) = plan {
    let comps = gregorian.dateComponents(
        [.year, .month, .day, .hour, .minute], from: first
    )
    return [UNNotificationRequest(
        identifier: "\(baseID)-first",
        content: content,
        trigger: UNCalendarNotificationTrigger(dateMatching: comps, repeats: false)
    )]
}
// 原有 repeating 分支保持不变
```

`workday` 分支在 `deferred` 时使用 `firstWorkday(onOrAfter: effectiveStart, calendar: gregorian)` 计算首发日。

**清理：** `notificationIdentifiers(for:)` 需要同时包含 `"\(baseID)-first"`，确保切换重复规则/删除事件时不留下幽灵通知。

### 回归测试


## D-05 记事编辑产生 `endDate == startDate`

### 根因

[EventEditView.swift:293-305](../Sources/LunisolarCalendarApp/Views/EventEditView.swift) 对记事设置 `end = startDate`，编辑分支直接 `copy.endDate = end`，绕过 `CalendarEvent` 构造器的兜底。`EventStore.merge` 又以 `endDate <= startDate` 判 invalid（[EventStore.swift:647-653](../Sources/LunisolarCalendarApp/Stores/EventStore.swift)）。

### 修复策略

把“记事结束时间”的合法化收口为一个纯函数，UI 保存与存量修复共用：

- `end > start` 是不变量；
- 记事不展示时长，取最小合法值（非全天 +1 秒，全天 +86399 秒）；
- 在 `EventStore.load()` 做一次存量修复，避免旧数据继续被导出/导入丢弃。

### 具体改动

**文件：** [CalendarEvent.swift](../Sources/LunisolarCalendarApp/Models/CalendarEvent.swift) 增加：

```swift
/// 记事不参与时长展示，但必须满足 endDate > startDate 的存储不变量。
public static func normalizedEnd(forNoteStartingAt start: Date, isAllDay: Bool) -> Date {
    start.addingTimeInterval(isAllDay ? 86_399 : 1)
}
```

**文件：** [EventEditView.swift:293-296](../Sources/LunisolarCalendarApp/Views/EventEditView.swift)

```swift
var end = endDate
if type == .note {
    end = CalendarEvent.normalizedEnd(forNoteStartingAt: startDate, isAllDay: isAllDay)
}
if end <= startDate {
    end = startDate.addingTimeInterval(isAllDay ? 86_399 : 1)
}
```

**文件：** [EventStore.swift](../Sources/LunisolarCalendarApp/Stores/EventStore.swift) 在 `load()` 解码成功后加：

```swift

for i in events.indices where events[i].endDate <= events[i].startDate {
    events[i].endDate = CalendarEvent.normalizedEnd(
        forNoteStartingAt: events[i].startDate,
        isAllDay: events[i].isAllDay
    )
}
```

（修复后照常重建 `idToIndex` / 排序缓存；若库内本无非法数据不产生额外写盘。）

## D-06 “删除所有数据”行为与文案不符

### 根因

[SettingsView.swift:196-211](../Sources/LunisolarCalendarApp/Views/SettingsView.swift) 文案承诺“删除所有日程、提醒和设置”，实际 [EventStore.clearAll](../Sources/LunisolarCalendarApp/Stores/EventStore.swift#L700-L721) 只清事件；倒数日与 7 个 `@AppStorage` 设置都保留。

### 修复策略（二选一）

**方案 A（推荐，发布安全）——把文案改成与实际一致**

- Label：`删除所有日程`
- Footer：`将永久删除所有日程及其提醒，此操作无法撤销。外观、周起始日等设置不会重置。`
- 清空成功 Toast 保持“已清空 N 条日程”。

优点：改动最小、不引入误删设置的风险；与按钮实际行为 100% 一致。

**方案 B（仅当产品明确要求“恢复出厂”）——实现真正的全清**

1. `CountdownStore` 增加批量清空（当前只有逐个 `delete`）：

```swift
@discardableResult
public func removeAll() -> Int {
    let n = events.count
    for ev in events {
        #if canImport(ActivityKit) && canImport(WidgetKit) && !os(macOS)
        CountdownActivityManager.end(for: ev.id)
        #endif
    }
    events.removeAll(keepingCapacity: true)
    saveNow()
    return n
}
```

2. `EventService` 增加：

```swift
@discardableResult
public func clearAllData() -> (events: Int, countdowns: Int) {
    let e = store.clearAll()
    let c = countdownStore.removeAll()
    SettingsRegistry.resetAll()
    NotificationManager.shared.cancelAll()
    return (e, c)
}
```

3. 新增 `SettingsRegistry`，集中登记并重置全部键：


4. 确认弹窗改为列出将删除的类别与条数（日程 N、倒数日 M、设置将恢复默认），并明确“iCloud 中的远端数据也会被墓碑删除”。

建议：**本次发布采用方案 A**；方案 B 需要单独的产品确认与一轮完整回归（尤其 CloudKit 墓碑和 App Group 快照）。

- 方案 A：本地化 key 四语言存在；UI 文案断言。
- 方案 B：`testClearAllDataRemovesEventsAndCountdownsAndResetsKeys`；确认 `clearAll` 仍打墓碑、通知全部取消。

**验收：** 危险操作的标题、footer、实际行为三者一致；不存在“说删设置但没删”的承诺落差。

## D-07 AI 归一化裸替换 am/pm

### 根因

[AICommandParser.swift:538-540](../Sources/LunisolarCalendarApp/Services/AICommandParser.swift)：

```swift
s = s.replacingOccurrences(of: " AM", ...)
     .replacingOccurrences(of: " PM", ...)
     .replacingOccurrences(of: "am", with: "上午")
     .replacingOccurrences(of: "pm", with: "下午")
```

裸替换没有词边界，`team`、`example` 里的 `am` 被改写；`3pm` 变成 `3下午` 后没有“点/时”锚点，`parseClock` 无法识别，回落 09:00。

### 修复策略

只转换**紧邻数字**的 am/pm，并直接生成中文时间表达式：

- `3pm` → `下午3点`
- `3:30pm` → `下午3:30`
- `3 am` → `上午3点`

## D-08 ICS 的 RECURRENCE-ID / EXDATE / RRULE 细节丢失

### 根因

[DataPortability.swift:346-347, 381-387, 520-538, 581-608](../Sources/LunisolarCalendarApp/Support/DataPortability.swift)：

- 不解析 `RECURRENCE-ID`；主事件与例外事件的 `pseudoUUIDForImport` 只用 UID 做种子 → 同 UUID → 例外覆盖主事件。
- 不解析 `EXDATE`。
- `parseRRULE` 只取 `FREQ`，忽略 `INTERVAL/COUNT/UNTIL/BYDAY`。

### 修复策略（分两阶段）

**阶段一（本次 P2 收口，不改存储 schema）**

1. 解析 `RECURRENCE-ID`，让例外事件拥有独立 UUID，并作为**一次性事件**导入：
   - 种子变为 `uid:<uid>|rid:<recurrence-id>`；
   - `repeatRule = .never`，标题可保持原样；
   - 主事件 UUID 种子保持原样，避免存量重复导入产生副本。
2. `RRULE` 若含 `INTERVAL != 1`、`COUNT`、`UNTIL` 或非工作日型 `BYDAY`，仍按最接近的 FREQ 导入，但在 `notes` 追加一行可读提示：
   `[原重复规则已简化：FREQ=WEEKLY;INTERVAL=2]`
3. `EXDATE` 解析后同样追加提示：`[已忽略 N 个排除日期]`（阶段二再真正支持）。

> 阶段一解决“数据互相覆盖”和“静默错误”，不追求完整语义。

**阶段二（独立迭代，需 schema 迁移）**

1. `CalendarEvent` 增加可选 `RecurrenceSpec`（`interval`、`count`、`until`、`excludedDates`），使用自定义 `init(from:)` + `decodeIfPresent` 保证旧库可读；
2. `occurs(on:)` 应用 interval/count/until/excludedDates；
3. 通知层按 `until`/`count` 停止调度，避免无限重复；
4. `parseRRULE` 返回完整 spec；`EXDATE` 写入 `excludedDates`；
5. 导出时还原完整 RRULE/EXDATE。

### 具体改动（阶段一）
