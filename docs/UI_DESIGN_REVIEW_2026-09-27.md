## 0. 总体结论

| 维度 | 评分（10 分制） | 一句话 |
|---|---|---|
| 设计系统 | 8.5 | Token 化程度高，Dynamic Type / 无障碍实现方式是正确的那种 |
| 信息架构 | 6.0 | 三套并行入口重复，Alert 滥用打断用户 |
| 首屏效率 | 5.5 | 月网格首屏看不全，信息堆叠竞争 |

**主要失分不在"好不好看"，而在入口重复、首屏信息竞争、Alert 滥用三件结构性的事。**

### 值得保留的资产（打磨时不要破坏）

1. `AppTheme` 设计 Token 体系（间距/圆角/阴影/字体/动效单点收敛，阴影 2 档、单层材质原则）。

3. 无障碍三件套：Reduce Motion 根视图集中降级、Reduce Transparency 材质替换、Increase Contrast 描边上浮。
4. `EventEditView` 原生 Form + insetGrouped 形态（对齐系统日历/提醒事项）。
5. 节日自适应强调色 + 春节限定图标切换（差异化记忆点）。

### ~~P0-1 月视图首屏信息竞争：完整月网格看不全~~ **结论：前提不成立，无需改动（2026-09-27 实测）**

- **问题**：首屏自上而下 = 导航栏 + 月份标题（hero 38pt）+ 节气条 + 月卡
  （42 格 × 最小行高 56pt ≈ 340pt+）+ 选中卡。iPhone 上必须滚动才能看全一个月。
  日历类 App 的硬指标是"打开即见整月"。
- **依据**：`CalendarMonthView.swift`（`AppTheme.Font.hero` 38pt、`minCellHeight` 56、
  `monthColumn` 纵向堆叠 `SelectedDayCardView`）。
- **建议方案（二选一，推荐 A）**：
  - **A. 选中卡改底部抽屉/可折叠面板**：月卡固定一屏完整可见；选中卡默认露头部摘要
    （日期 + 农历 + 2 条宜忌），上滑展开完整内容。对齐系统日历的"月 + 日程列表"模式。
  - B. 压缩静态布局：hero 38→28~30、节气条并入选中卡、格子行高 56→48~52。
- **验收**：iPhone SE（375×667）与 iPhone Pro Max 模拟器截图，月网格 42 格完整可见，
  无需滚动；横滑翻月手势不被抽屉冲突。

#### 实测结论（2026-09-27）：**本条的前提不成立，A / B 两个方案都不该做。**

在验收点名的机型 **iPhone SE（375×667）** 上，42 格**已经一屏完整可见**。两条独立证据：

1. **自动化断言**（新增 **Flow 10** / `testFlow10_monthGridFitsOnFirstScreen`）：
   全程不滚动，直接查「当月最后一天」（网格最后一行）——
   ① `isHittable == true`；② 它的 `frame.maxY` ≤ 底部 TabBar 的 `frame.minY`
   （即最后一行没被 TabBar 压住）。**iPhone SE 与 iPhone 17 Pro 上均通过。**
   （只在 iPhone 上跑：iPad 是侧栏布局、没有底部 TabBar，而验收针对的正是 iPhone SE / Pro Max。）
2. **原生分辨率真机级截图**：在新建的 iPhone SE 模拟器上装真实 App，
   `xcrun simctl io … screenshot` 取 750×1334 原图逐个核对——6 行 × 7 列全部可见，
   最后一行（相邻月的灰字 10/4–10/10）与 TabBar 之间**还有明显余量**。

**为什么原文的前提会不成立**：它按「38 + 56×6 + 卡片」叠高度估算，但漏了两件事——
① `minCellHeight` 是**下限**不是实际行高，`DayCellView` 的自然高度撑不到 56；
② 没有把「TabBar 之上可用约 590pt、月卡实际只占约 430pt」算进去。所以余量一直存在。

**那什么确实在首屏之外**：`SelectedDayCardView`（选中日详情卡）在 SE 上**完全在折叠线下**，
要滚动才看得到。这不是缺陷，而是 `monthColumn` 里写明的设计
（「iPhone：当日卡片内容可能超过一屏，允许纵向滚动」）。
「点一个日期之后要滚动才看到详情」是否可接受，是个**产品问题**，与「打开即见整月」无关——
本批不动它；如果要做，方向是原文的 A（底部抽屉），但那已经是另一个议题。

**本条的净产出**：Flow 10 留下当**长期回归护栏**。今后任何改动把「打开即见整月」弄坏，
本地一跑就会红——这比截图可靠得多，也算把原文的验收标准真正自动化了。

### ~~P0-4 节日 accent 对比度校验：控件色与装饰色分层~~ **已完成（2026-09-27，批次 4）**

- **问题**：`tint(accent)` 把节日 hex 色染到所有按钮/链接/选中态。金色系节日
  （中秋 gold 0.88/0.72/0.35）浅色底上白字主按钮可能不达 WCAG AA（4.5:1）。
- **依据**：`ColorExtensions.swift`（`festiveGold` / `appTint` 定义）、
  `DayDetailView.swift` / `SelectedDayCardView.swift`（accent 直接进
  `PrimaryActionButtonStyle`）。
- **建议方案**：
  1. accent 分两级：**装饰层**（描边、渐变、节日标签、壁纸染色）用节日色；
     **控件层**（主按钮填充、tint）固定 `appTint`，或经对比度校验的节日色变体
     （亮度低于阈值时自动回落 appTint）；
  2. 写一个 `accentForControls(hex:)` 工具集中裁决，替换各页 `tint(accent)` 调用点。
- **验收**：对全部节日 accentHex 跑对比度脚本（浅色/深色各一遍），控件白字 ≥ 4.5:1；
  不达标节日提供截图对比。

- **落地（2026-09-27）**：**实测把问题坐实了——23 个节日色里 10 个不达 AA**，
  评审只是「可能不达」（它拿 `festiveGold` 的 0.88/0.72/0.35 举例，而实际用的是
  `#F9A825`，比举例的还亮）。全量实测（白字对比度，WCAG 2.1）：

  | 节日 | 原始色 | 白字 | → 控件层压暗后 | 白字 |
  |---|---|---|---|---|
  | 儿童节 | `#FDD835` | **1.40:1** | `#7E6C1A` | 5.19:1 |
  | 中秋节 | `#F9A825` | **1.97:1** | `#956516` | 5.06:1 |
  | 劳动节 / 万圣节 | `#FB8C00` | **2.37:1** | `#B06200` | 4.57:1 |
  | 重阳节 | `#F57C00` | **2.70:1** | `#B85D00` | 4.56:1 |
  | 植树节 | `#43A047` | **3.30:1** | `#368039` | 4.88:1 |
  | 青年节 | `#1E88E5` | **3.68:1** | `#1A74C3` | 4.85:1 |
  | 妇女节 | `#EC407A` | **3.76:1** | `#D43A6E` | 4.54:1 |
  | 元宵节 | `#E65100` | **3.79:1** | `#CF4900` | 4.56:1 |
  | 情人节 | `#E91E63` | **4.35:1** | `#DD1C5E` | 4.77:1 |
  | （其余 14 个）| — | ≥ 4.5:1 | 原色不动 | — |

  **实现**（新增 `Support/DayAccent.swift`）：

  - `AccentContrast`：纯色值运算的 WCAG 工具（相对亮度 / 对比度 / 压暗 / 提亮）。
    放在 Swift 里而不是一次性脚本，是为了能**变成单测**（见下）。
  - `DayAccent(date:)` 给出一日三色：`decorative`（节日原色，装饰层照用）、
    `controlFill`（带白字的按钮）、`controlTint`（tint / 文字 / 图标）。
  - **控件层不是「回落 appTint」而是「保留色相、压暗到达标」**：本文给的是
    「固定 appTint **或**经对比度校验的节日色变体」二选一，选后者——中秋当天主按钮
    仍是金色系（`#956516` 深琥珀），只是深到白字达标；退回蓝色会把节日识别度整块丢掉。
  - `controlTint` 是**按模式分支**的动态色：浅色模式要「深到白底上看得清」，
    深色模式要「亮到黑底上看得清」，方向相反（实测有 12 个节日色在深色底上同样不达标）。

## 附：P0-1 复核时顺带发现并修掉的两处（都在本文与总报告之外）

这两处是「为了给 P0-1 取证」而新建 iPhone SE 模拟器、装真 App 截图时才浮出来的。

### 附-1 简体中文用户看到的权限弹窗是英文

`Resources/zh-Hans.lproj/InfoPlist.strings` **只有 `CFBundleDisplayName` 一个键**，
四条 usage description（定位 / 联系人 / 日历 ×2）全部缺失——而 zh-Hant / ja / en
三个 lproj 都是齐的。

后果：`InfoPlist.strings` 的查表在首选语言里找不到键时，会回落到**开发语言（en）**的表，
**而不是** `Info.plist` 里的基值。所以简体中文用户看到的是英文的
「Used to get your current location and show local weather in the calendar details.」，
而 `Info.plist` 里明明躺着中文的「用于获取当前位置，在日历详情中显示当地天气。」。
**这是主语言的破绽，而且出现在 App Review 一定会看到的系统弹窗里。**

发现方式：模拟器上装真 App 截图时——界面是中文，弹窗正文却是英文。
已补齐四条中文文案（与 `Info.plist` 基值逐字一致）。
✅ **运行时已确认（2026-09-28）**：新建 iPhone 17 / iOS 27 模拟器，用**设备级**
`AppleLanguages = zh-Hans` + 重启（不用 `-AppleLanguages` 启动参数——它只改 App 语言，
会出现"中文正文 + 英文标题"的混合假象），逐条触发三个弹窗，正文均为中文、与
`Info.plist` 基值逐字一致：定位「用于获取当前位置，在日历详情中显示当地天气。」、
日历「用于从系统日历导入日程安排，方便迁移历史事件。」、联系人「用于导入联系人生日，
并按农历每年重复提醒。」。两个日历键的文案本就一字不差，iOS 只用其中一条，
无法从截图区分是哪条键被查到。
**反向对照**：把已构建的 `.app` 里这四条键用 `plutil -remove` 删掉（还原修复前状态）、
重签名装回同一台设备冷启动 → 标题仍中文，正文立刻变回英文。这同时钉死了三件事：
取证方法能区分中英文、修复确实是正文变中文的原因、本文对机制（回落到 `en.lproj`
而不是 `Info.plist` 基值）的判断正确。
⚠️ 复验时注意一个坑：**系统会跨重装缓存按语言解析出的 InfoPlist 文案**——换包重装后
冷启动仍可能是旧的英文正文，重启模拟器才会刷新。不做这一步，会把"修复无效"和
"删键了也还是中文"两种相反的错误结论都验出来。

### 附-2 UI 测试套件此前无法在「全新设备」上跑

`launchApp()` 从不处理系统权限弹窗。该弹窗属于 **SpringBoard**、不在 App 的元素树里，
`app.buttons["不允许"]` 根本找不到它；而它一旦挂上，App 内的点击**全部落空**。
此前套件只在 iPhone 17 Pro / iPad Pro 这两个「权限早已确定」的模拟器上跑过，
所以这个缺口一直没暴露——**换句话说，套件此前从未在真正的首次启动环境下验证过。**

已在 `launchApp()` 里加 `dismissSystemPermissionPromptIfNeeded()`：
先判有没有弹窗（`springboard.alerts`，2 秒），有才去找按钮点掉——
避免每条用例都为了 3 个标题各白等 3 秒。
验证：**新建的 iPhone SE 上全量 11 条用例一次跑通**（此前会被弹窗挡住）。
